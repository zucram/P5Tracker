# Track post-launch results

Use this guide for a launch check-in, feedback review, SEO follow-up, or support report. Read `.local/growth/status.md` first for the current campaign, private targets, access notes, and next review. If that ignored file is unavailable, report the missing context instead of inventing account data.

1. **Establish the window.** Record the observation time, reporting timezone, inclusive start/end dates, game, channel, and filters. Read the previous review in `.local/growth/reviews/`. Keep partial launch-day results separate from complete days.
2. **Inspect feedback.** Read the published thread and repository issues. Record actionable reports in `.local/growth/feedback.csv` with a source link, affected game/feature, severity, reproduction status, and next action. Prioritize lost saves, wrong deadlines or answers, then blocked navigation. Count repeated requests without treating votes as usage. Prepare replies for Marcus unless sending that specific reply is already authorized.
3. **Measure use.** In the authorized Umami property, compare total visitors, visits, and landing pages with campaign-filtered visitors. Separate `/p3/`, `/p5/`, and guide paths. Use unique `p3_tracker_used` visitors for Reload and `tracker_used` visitors for Royal. Inspect progress actions, guide-to-tracker paths, save failures, sharing, and support clicks using [event definitions](analytics.md). Record raw counts alongside rates. Only calculate conversion from visitors in the same filtered cohort. If cohort or ordered-funnel data is unavailable, label it unavailable.
4. **Check search and support.** Use an existing authorized Search Console property for indexing, query impressions, clicks, and CTR. Treat Trends as relative interest, not search volume. Reconcile actual Ko-fi receipts and fees in their original currency. Support clicks are interest, not payments. Keep amounts, account links, exports, and private feedback in `.local/growth/`.
5. **Choose one next action.** Fix reproducible correctness defects first. If arrivals grow but manual use does not, investigate the landing page and first useful action. If use grows but support clicks do not, review support visibility before adding prompts. If clicks grow without receipts, inspect checkout and the support offer. Treat small samples as inconclusive. Expand content from demonstrated player needs and search evidence.
6. **Close the review.** Save `.local/growth/reviews/YYYY-MM-DD.md` with source timestamps, counts, unknowns, feedback, the chosen action, and next review date. Update the private status and metrics ledger. For shipped fixes, update the owning data/docs and record commit, checks, deployment, and live verification. Finish with what changed, what remains unknown, and what happens next.

Use next-day and 72-hour checks for launch defects, a seven-day check for engagement, and matched complete 28-day windows for trends. These are review checkpoints, not a running monitor. Create scheduled work only when requested.

Preserve player saves and source provenance. Stub analytics during tests. Keep public responses, post edits, crossposts, spending, and account changes within their explicit authorization. Recheck community rules before new posts; a previous post's acceptance is not blanket permission.
